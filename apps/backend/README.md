# Серверная часть

Общая система на Python + Django + PostgreSQL. Выбрана модульная организация одного приложения: бот, веб-обработчики и фоновые исполнители используют общие операции и правила. Базовые зависимости этапа 1А зафиксированы в [requirements.txt](requirements.txt). Серверный проект и миграции описаны в плане §29.

## Базовые зависимости

Из корня репозитория:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r apps/backend/requirements.txt
.venv/bin/python -m pip check
```

Установка и загрузка адаптера PostgreSQL проверены на Python 3.14.5 в macOS.

## Локальный запуск этапа 1А

Нужна локальная база PostgreSQL и отдельная роль для разработки. Для команды тестов роль должна уметь создавать тестовую базу. Из корня репозитория создайте `.env` на основе `.env.example`, заполните `DJANGO_SECRET_KEY` и `DATABASE_URL`. Ключ можно сгенерировать командой `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`.

```sh
. .venv/bin/activate
set -a
. ./.env
set +a
bash apps/backend/scripts/build_static.sh
python apps/backend/manage.py migrate
python apps/backend/manage.py runserver
```

Стартовая страница открывается по адресу `http://127.0.0.1:8000/`. Для проверки сборки без отладки выполните `APP_ENV=production python apps/backend/manage.py collectstatic --noinput`. Веб-сервер рабочей среды раздаёт только каталог собранной статики `data/staticfiles`.

Очередь запускается командой `python apps/backend/manage.py run_worker`. Она выполняет зарегистрированные внутренние обработчики. Список `BACKGROUND_TASK_HANDLERS` на этапе 1А пуст. Команда с `--once` выполняет доступные задачи и завершается. Обработчик готовит результат вне транзакции и возвращает функцию для записи в БД. Воркер сохраняет результат и завершает задачу в одной транзакции. Внешние отправки подключаются отдельным контрактом на этапе 1В.

Закрытые объекты хранятся в `data/cas` либо в каталоге из `CAS_ROOT`. Сервис выдачи проверяет переданное решение о доступе до открытия файла. Маршрут выдачи подключается вместе со связью объекта с прикладной записью.

Тесты на PostgreSQL:

```sh
python apps/backend/manage.py test apps/backend
python apps/backend/manage.py makemigrations --check --dry-run
```

### Серверные копии вложений поддержки

После миграций команда `python apps/backend/manage.py run_support_attachments --cleanup-only`
снимает просроченные ссылки и очищает невостребованные объекты. Для разового прохода
добавьте `--once`. Срок доступности копии составляет 168 часов с момента подготовки,
физическая очистка CAS учитывает ссылки, выдачи и возраст файлов. Каталог `CAS_ROOT`
должен быть закрыт от прямой раздачи и находиться на устойчивой локальной файловой системе.

Получение из ВК включайте на тестовом стенде через `VK_ATTACHMENT_FETCH_ENABLED=1` и
`VK_ATTACHMENT_HOSTS` со списком точных проверенных имён CDN через запятую. Затем
запустите `python apps/backend/manage.py run_support_attachments`. Загрузчик не
переходит по перенаправлениям и не обновляет истёкшие ссылки. Пока канал выключен,
сетевые проверки выполняются с подставным источником.

Перед открытием восстановленного кабинета, после остановки прежних процессов и выбора
изолированной пары БД и CAS, выполните `run_support_attachments --recover-restored`.
Команда отменяет незаконченные подготовки, снимает старые защиты чтения и закрывает
просроченные копии. На стенде проверьте лимит времени передачи в веб-сервере и чтение
аудио диапазонами. Код Django ограничивает чтение из CAS пятью минутами.

### Восполнение истории после разрыва Long Poll

Пока `VK_GAP_HISTORY_VERIFIED=0`, новые разрывы сразу требуют ручного разбора.
После проверки методов на тестовом сообществе включите этот параметр и запустите
`python apps/backend/manage.py run_vk_gap_history` с настроенными `VK_GROUP_ID`
и токеном. Воркер ограничивает число диалогов и страниц. Общая квота со сверкой
ответов составляет 12 чтений за минуту на сообщество. Отчёт в `LongPollGap.coverage`
сохраняет просмотренный диапазон и причины неполного покрытия.

После восстановления БД вызовите `mark_restored_vk_gaps` из карантина до запуска
читателя. Когда читатель подтвердит порцию нового периода и координатор разберёт
оставшиеся пропуски, оператор фиксирует согласованное решение:

```sh
python apps/backend/manage.py resume_vk_gap --gap-id GAP_ID --profile-id COORDINATOR_ID \
  --period PERIOD --position CONFIRMED_TS --notes 'Основание и оставшиеся пропуски'
```

Команда сверяет текущий период, подтверждённую позицию и права профиля координатора.
События, сохранённые во время паузы, остаются на ручном разборе.

### Кнопки студента в ВК

Сетевой режим выключен по умолчанию. На тестовом сообществе после проверки
`message_event` и формата короткого подтверждения включите `VK_CLICK_ANSWERS_VERIFIED=1`.
Приём `run_vk_long_poll` сохраняет нажатия, `run_worker` применяет их к карточкам,
а `run_vk_click_answers` отдельно отправляет короткие подтверждения. При включённом
режиме ответ менеджера содержит кнопку «Вопрос решён». У неё локальный срок семь дней.
Истечение 10-секундного срока подтверждения не отменяет действие студента.

### Восстановление отправок поддержки

Команды сервера и CAS требуют Linux/macOS (на Windows используйте Linux-контейнер
или WSL: хранилище использует `fcntl`). Перед обработкой восстановленной БД
остановите прежние экземпляры приложения и все источники записи, отключите внешние
отправки и оставьте восстановленный контур изолированным. Установите
`STAFF_QUARANTINE_INCIDENT`, выполните миграции и сохраните один UUID запуска
восстановления в журнале оператора. С тем же UUID выполните:

```sh
python apps/backend/manage.py recover_support_delivery --recovery-run-id UUID
```

Команда сначала сохраняет запуск, затем одной транзакцией обрабатывает группы
поддержки. Незавершённые отправки становятся `unknown_outcome`, включая попытки
с пустым `started_at`. Незавершённые сверки завершаются как
`unresolved/recovered_from_backup`, а их задания — как `failed`. Прежние аренды
отзываются очисткой токена и срока: старый исполнитель не пройдёт проверку владения.
Каждый восстановленный ответ `failed` получает индивидуальную блокировку.
Противоречивые связи или подтверждённые исходы вызывают откат всей обработки;
запуск остаётся незавершённым. До разбора ошибки карантин снимать нельзя.

Повтор завершённого UUID ничего не меняет, в том числе не блокирует новые ответы.
Для нового восстановления нужен новый UUID; прежняя активная блокировка заменяется,
а её запоздалый результат не применяется. Эта команда обрабатывает только отправки
поддержки. Остальные шаги холодного старта — права, сеансы, CAS, курсоры и проверка
предметной копии — выполняются отдельно по §9.4.2 до открытия кабинета.

После общей сверки и снятия карантина индивидуальные запреты остаются видны в карточке.
Действие «Проверить историю ВК» ставит отдельное задание чтения. Его исполнитель:

```sh
python apps/backend/manage.py run_support_sender --reconcile-only --once
```

При заданном `VK_GROUP_ID`, но выключенном `VK_HISTORY_CORRELATION_VERIFIED` либо
отсутствующем токене выполняется только локальная проверка отсутствия допуска в
актуальной БД. Если этого недостаточно, сохраняется `unresolved/history_unavailable`.
Восстановленные записи не допускают отрицательного вывода по пустому `started_at`
или отсутствию сообщения. Для сетевого чтения нужны подтверждённая на пилоте
корреляция и токен; `messages.send` сверка не вызывает.

Найденное однозначное подтверждение снимает индивидуальный запрет вместе с записью
факта отправки; прежние отказы и черновик сохраняются. Доказательство неотправки
за весь затронутый восстановлением интервал требует проверенного внешнего источника.
Такого источника пока нет: пустая история сохраняет блокировку без срока снятия.

### Главная кабинета и личные уведомления

После применения миграций сотрудник с действующим рабочим допуском открывает на `/`
свои обращения, общую свободную очередь и сводку поддержки в пределах своего доступа.
Ошибка отдельного блока показывается отдельно от пустого списка; блок можно загрузить
повторно. Сотрудники без допуска продолжают видеть вход и состояние своей заявки.
Ближайшие занятия, мероприятия и адресные пометки появятся вместе со своими модулями.

Миграция `workspace/0001_initial` добавляет личные уведомления. Новое назначение,
перехват и передача координатором создают уведомление новому владельцу в одной
транзакции с событием. Точный повтор команды, взятие уже своего обращения и возврат
в свободную очередь не создают дополнительного личного уведомления. Исторические
назначения при миграции сохраняются без создания новых уведомлений задним числом.

`GET /staff/notifications/` открывает ленту. При `Accept: application/json` возвращает
`notifications`, `unread_count`, `total_count`, `page` и `next_page`; страница содержит
до 30 записей. Получатель определяется по действующему сеансу. Новые события и история
доступны через общую навигацию; внешний канал уведомлений сотрудникам не используется.

Открытие записи отправляет защищённый CSRF запрос
`POST /staff/notifications/{id}/read/`. Первое прочтение сохраняет серверное время,
повтор возвращает то же значение. HTML-форма работает и без JavaScript: после записи
сервер отвечает `303` на адрес исходного обращения. Для JSON возвращаются
`notification` и `changed`. Чтение чужой записи отклоняется, а доступ к исходной карточке
проверяется отдельно при переходе. Прочтение не меняет назначение или статус обращения.

### Материалы: текстовые черновики (начало 1Г)

После `python apps/backend/manage.py migrate` раздел `/knowledge/materials/`
доступен сотрудникам с действующим доступом к поддержке. Из общей навигации можно
создать материал с первым черновиком, открыть редактор или добавить независимый
черновик того же материала. HTML-формы работают без JavaScript.

Поддерживается только введённый текст: до 64 КиБ UTF-8, название до 200 символов,
описание до 2000, до 20 меток по 64 символа. Тело команды ограничено 512 КиБ,
чтобы допустимый текст проходил после кодирования формы или JSON. Пустой текст
можно сохранить для дальнейшей работы. Файлы и таблицы пока не принимаются.

Маршруты возвращают JSON при `Accept: application/json`; POST также принимает
JSON либо обычную URL-кодированную HTML-форму с CSRF. Создание материала:
`POST /knowledge/materials/`; создание отдельного черновика:
`POST /knowledge/materials/{material_id}/drafts/`; чтение и сохранение:
`GET/POST /knowledge/materials/{material_id}/drafts/{version_id}/`.
Для открытия формы нового черновика используется GET на путь создания черновика.

Каждый POST принимает `client_operation_id` и поля `title`, `description`, `tags`,
`source_type=text`, `source_text`. Необязательные поля можно опустить. В JSON метки
передаются массивом строк; в форме — через запятую. Сохранение дополнительно
требует `expected_draft_revision`. Конфликт даёт `409 draft_revision_conflict`;
HTML сохраняет ввод в форме и показывает текущие данные для сравнения. Разные
черновики имеют независимые ревизии. Сохранение не обновляет базовую ревизию публикации.

UUID уникален в пределах сотрудника для всех команд материалов. Точный повтор
возвращает прежние ID и исходную `saved_draft_revision` вместе с текущим черновиком;
он не сохраняет старый текст поверх последующих правок. Другой запрос с тем же UUID
получает `409 operation_mismatch`. Право работы проверяется и при повторе.

Миграция `knowledge/0001_initial` создаёт `kb_document`, `kb_document_version`
и `kb_command`. В журнале сохраняются автор, время, намерение команды и ревизия.
Подготовка, индексация, публикация, поиск и генерация AI этим блоком не включаются.
Черновики пока имеют состояние `not_prepared` и не доступны боту.

Текстовый черновик можно подготовить через его карточку или командой
`POST /knowledge/materials/{material_id}/drafts/{version_id}/prepare/`.
Передайте `client_operation_id` и `expected_draft_revision`. Запустите
`python apps/backend/manage.py run_worker`, чтобы обработать задание.
Предпросмотр показывает сохранённый текст подготовленной ревизии. Состояние
`source_prepared` означает, что снимок текста создан. Готовность индекса и
публикация проверяются отдельными операциями.

Для индексации установите `apps/backend/requirements-index.txt`. PostgreSQL должен
предоставлять расширение `vector`. Если роль миграций не может создать расширение,
администратор базы заранее выполняет `CREATE EXTENSION vector`.

Загрузите `tokenizer.json` и `onnx/model.onnx` из
[закреплённой ревизии E5](https://huggingface.co/intfloat/multilingual-e5-small/tree/614241f622f53c4eeff9890bdc4f31cfecc418b3)
в отдельный локальный каталог и задайте его через `KNOWLEDGE_E5_ROOT`.
Воркер проверяет SHA-256 обоих файлов перед началом работы.

```sh
OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 ORT_NUM_THREADS=2 TOKENIZERS_PARALLELISM=false \
  nice -n 10 python apps/backend/manage.py run_worker --knowledge-index-only
```

Обычный `run_worker` готовит исходный снимок и ставит задачу индексации. Отдельный
воркер формирует поколение из этого снимка. На рабочем Linux дополнительно задайте
`CPUQuota=200%` для службы индексации. В кабинете готовность видна после обновления
страницы. Индексированные фрагменты ждут явной публикации.

Когда индекс готов, откройте черновик, проверьте подготовленный текст и выберите
«Опубликовать просмотренный снимок». Из карточки действующей версии можно снять
публикацию. Если за время работы черновика действующая версия изменилась, сначала
сверьте черновик с публикацией и подготовьте новый снимок.

В восстановленной БД запустите `isolate_restored_knowledge` во время карантина,
до его снятия. Восстановленные публикации исключаются из выдачи. Чтобы вернуть
материал в поиск, сотрудник проверяет текст, готовит и публикует новый снимок.

Из обращения можно искать по опубликованным материалам и вставлять фрагмент в
черновик ответа. Действие «Создать черновик материала из обращения» предлагает
выбрать вопрос и подтверждённый ответ сотрудника, затем создать новый материал
или выбрать существующий. Перед публикацией уберите частные сведения из текста.

Для пилотного Long Poll задайте `VK_LONG_POLL_PILOT_PEER_ID` в локальном
`.env`. Читатель требует числовой ID диалога перед обращением к ВК и сохраняет
только события этого диалога. События вне пилота отбрасываются до журнала,
карантина и очереди. При разрыве общий поиск по истории сообщества выключен.

После загрузки `.env` и миграций одну порцию можно проверить командой
`VK_LONG_POLL_ENABLED=1 python apps/backend/manage.py run_vk_long_poll --once`.
Для непрерывного чтения уберите `--once`. Переменная перед командой действует
только на этот запуск.

Для локальной диагностики поиска включите `SUPPORT_AI_LOOKUP_ENABLED=1` и
настройте `KNOWLEDGE_E5_ROOT`. Обычный `run_worker` фиксирует версии вопроса,
а `python apps/backend/manage.py run_support_ai_lookup` выполняет поиск.
Итоги без ответа доступны в разделе «Поддержка → Журнал автоматической помощи».
Вопросы после диагностики остаются доступны для ручного разбора.

### Общая оценка качества ответа

После `python apps/backend/manage.py migrate` (новая миграция
`support/0020_ai_answer_review`) карточка сохранённого ответа показывает
«Есть проблема», комментарий и историю сохранений. Любой сотрудник с текущим
доступом к записи может изменить общую оценку или снять пометку коллеги.
Источники показаны в сохранённых версиях; текст ответа и состояние доставки
оценка не меняет. Фильтр журнала `result=problem` выбирает действующие пометки.

`GET/HEAD /support/ai-answers/{answer_id}/review/` читает оценку без создания строки.
POST принимает только JSON с `client_operation_id`, десятичной строкой
`expected_review_revision`, булевым `problem_flag` и строкой `comment`
(до 2000 кодовых точек Unicode, может быть пустой). Сессия и CSRF обязательны.
Новая команда увеличивает ревизию и атомарно сохраняет историю. Точный повтор
UUID возвращает исходную `applied_revision` и отдельно актуальную оценку.
Конфликт ревизии требует явного сравнения; форма сохраняет локальный комментарий.
При потере ответа повторяется прежний UUID с прежними данными.

История доступна на странице ответа по 50 записей. Откат миграции при наличии
оценок/истории отклоняется до удаления таблиц: перед возвратом старого кода
нужно отдельно спланировать перенос этих данных.

### Генерация и доставка ответов

Для предпросмотра генерации запустите локальный llama-server на адресе loopback.
Задайте `MODEL_BASE_URL` с портом, `MODEL_NAME` и `MODEL_SHA256` выбранного
артефакта. Включите `SUPPORT_AI_GENERATION_ENABLED=1` вместе с диагностическим
поиском. Сохранённые ответы появятся в журнале автоматической помощи. Состояние
«Ожидает отправки» относится к отдельной записи доставки.

Для автоматической передачи вопросов без надёжных сведений предусмотрен
`SUPPORT_AI_HANDOFF_ENABLED=1`. После поиска без результата или завершённого
решения модели `{}` сохраняется поручение и выполняется передача текущего
контекста в одну карточку. Незавершённый или некорректный ответ модели получает
`model_unavailable`. Установленное поручение сохраняет первоначальные версии
вопросов и общий бюджет подготовки и доставки в 30 секунд. Этот бюджет
предварительный и требует измерения на пилоте.

Запустите `python apps/backend/manage.py run_support_handoffs` вместе с
исполнителем поиска. Параметр `--once` обрабатывает доступные таймеры и
просроченные поручения. Резервный проход подбирает просроченные записи даже
при потерянном задании. Уточнение исключает прежнее основание только своего
вопроса, пересчёт срока создаёт новую ревизию таймера. Сохранённые поручения
продолжают закрывать допуск отправок после своего срока.

Карточка показывает неизменяемый перечень работы на момент передачи.
Доставка сохраняет исходную карточку для позднего подтверждения VK.
Сервис связывает поручение с сохранённым ответом и набором его частей.
Карантин восстановления останавливает исполнитель.

По §10.5 локальная модель может подготовить до четырёх дословных выдержек
и явно выделить оставшиеся вопросы. Формат завершённого решения:

```json
{"parts": [{"fragment_id": 123, "quote": "Дословный текст источника"}], "remaining_work": ["Неотвеченная часть исходного вопроса"]}
```

Каждая выдержка проверяется по соответствующему предложенному фрагменту,
каждый элемент остатка должен дословно присутствовать в исходном вопросе.
Полный ответ содержит пустой `remaining_work`; отсутствие надёжного ответа
обозначается `{}`. Неверный или незавершённый JSON не устанавливает причину
передачи. Инструкция запрещает использовать противоречивые сведения и отвечать
на часть, достоверность которой зависит от неизвестного условия. Семантическое
качество разделения проверяется на вопросах клуба при пилоте.

Текущая попытка работает с одной сохранённой версией вопроса, которая может
содержать несколько вопросов в одном сообщении. Декомпозиция нескольких
независимых записей запросов в одну генерацию этим блоком не вводится.
Остаток сохраняется в существующем поручении одновременно со снимком ответа,
источниками и доставками. Выдержки сопровождаются названием источника;
отдельная часть сообщает студенту, какие вопросы передаются менеджеру.
Служебная часть не получает связь содержательного ответа с вопросом.
Статус `answered_partial` означает подготовку, а не подтверждённую доставку.
Журнал показывает остаток, состояние поручения и исход каждой отправки.

Частичные ответы требуют `SUPPORT_AI_HANDOFF_ENABLED=1`. Если передача выключена,
такой результат не отправляется и отмечается `handoff_not_enabled` для ручного
разбора. После передачи статус запроса остаётся `escalated_to_human`.
Завершение цепочки или общий срок передаёт остаток и неподтверждённые части
менеджеру; неизвестный исход не разрешает повтор отправки. Уточнение отменяет
прежнее основание, а просьба человека прерывает подготовку немедленно.
Ответ, полученный на границе срока, может остаться сохранённым проектом
с отменённой доставкой для менеджера.

Версия инструкции модели — 2, выход ограничен 1200 токенами; выдержка —
800 символами, суммарный остаток — 800 символами. Вход по-прежнему ограничен
четырьмя найденными фрагментами и 10 000 байтами их текста. Реальные задержка,
память и полнота обработки в контексте выбранной модели требуют пилота.

По §10.6 сообщения с вложениями также входят в автоматический текстовый контур.
Для голосового, фото или файла без текста сохраняется фиксированная просьба
описать вопрос текстом и написать «Позвать менеджера», если нужна помощь
сотрудника. Эта просьба не вызывает поиск или модель и сама не создаёт
человеческое обращение. Запрос остаётся ожидающим уточнения, а журнал отдельно
показывает подготовленную просьбу и состояние её доставки.

Текст вместе с вложением проходит обычный поиск по доступному тексту.
Модель получает признак `has_unread_attachments` и дополнительную инструкцию
версии `attachment_context_version=1`: содержимое вложений не передано и
не должно описываться как прочитанное. В модель не передаются файлы, адреса
их получения или учётные данные. Независимая часть текста может получить
подтверждённый ответ; остаток передаётся по §10.5 вместе с исходными вложениями.
Если надёжного текстового ответа нет, бот просит описание и предлагает человека.
Сбой поиска или модели сохраняет собственную причину и не выдаётся за
установленное отсутствие сведений.

Служебная просьба использует существующую доставку частей с отдельным серверным
профилем `attachment_text_request_v1`. До отправки проверяются фиксированный
текст, серверные метаданные и связь с исходным вложением. Обычный ответ
по-прежнему требует актуальных опубликованных источников. Общие проверки
режима, версии вопроса, пилотного диалога, неизвестности и восстановления
применяются к служебной просьбе. После выбора менеджера исходное вложение
попадает в ту же карточку, а новые вложения в человеческом режиме не запускают AI.
Скачивание и просмотр защищённых копий остаются отдельным контуром §16.24–16.25.

Для действий над автоматическим вопросом по §10.7/§19.3 примените миграции
`support/0019_request_resolution` и `vk_channel/0005_request_actions` штатной
командой `python apps/backend/manage.py migrate`. Существующие кнопки человеческих
карточек сохраняют свою цель. Новая кнопка хранит ID автоматического вопроса
и ожидаемую версию; в VK payload по-прежнему передаётся только UUID действия.

При `VK_CLICK_ANSWERS_VERIFIED=1` бот сохраняет клавиатуру вместе с сетевым
допуском части. Вызов менеджера доступен на каждой части, подтверждение решения —
на последней части полного содержательного ответа. Частичный ответ и просьба
описать вложение предлагают только менеджера. Старое действие после уточнения,
восстановления, истечения срока или смены несвязанного цикла не меняет новую цель.
Срок семь дней предварительный и требует проверки на пилоте. Callback-подтверждение
исполняется прежней командой `run_vk_click_answers` и не добавляет реплику в чат.

Подтверждение AI-вопроса хранит `resolved_at` и `resolved_by_vk_id` отдельно от
результата подготовки и доставки. Оно отменяет неначатую работу только этого
вопроса; независимые запросы продолжают работу. Допущенная отправка сохраняет
поздний исход, в том числе неизвестность. Нажатие не доказывает, что транспортный
исход неизвестной отправки установлен. Журнал отдельно показывает решение студента.
Вызов менеджера передаёт исходный вопрос, фактически отправленный текст
частей и текущий принятый контекст. Повтор использует ту же ещё открытую карточку
исходного цикла; другая новая карточка защищена от старой кнопки.

Обратная миграция `vk_channel/0005` проверяет отсутствие новых данных до удаления
колонок. Если уже есть действия AI-вопросов, подтверждения решения или клавиатуры
доставок, откат схемы останавливается с сохранением данных. Для возврата к прежнему
стеку требуется проверенная копия и общий порядок карантина восстановления;
удаление истории ради обратной миграции не выполняется автоматически.
Для продолжения закрытой карточки примените также
`vk_channel/0006_continuation_activation`. При пилотном флаге ответ менеджера
содержит две кнопки: «Вопрос решён» и «Вопрос не решён». Вторая видна сразу,
но до закрытия отвечает «Обращение ещё открыто.» и не расходует действие.
Сервер сохраняет точную карточку и следующую ожидаемую версию режима.
Закрытие менеджером или студентом в одной транзакции фиксирует исходное
`closed_at` у подготовленного действия и снимает `awaiting_close`.
Клавиатура и отправленный текст не переписываются. Срок действия не продлевается.
Истёкшее действие или закрытие в другой версии режима не активируют кнопку.

После закрытия нажатие создаёт одну дочернюю карточку с `parent_ticket_id`
либо возвращает уже открытую карточку того же продолжения, сохраняя её владельца
и время создания. Другая новая тема защищена от старой кнопки. Повтор старого
транспортного события раннего нажатия сохраняет прежний результат;
после закрытия требуется новое нажатие. Нажатия и короткие подтверждения
по-прежнему не создают реплики чата.

Текстовый путь §10.7 использует полные нормализованные фразы «Вопрос не решён»,
«Мой вопрос не решён», «Вопрос остался нерешённым», «Проблема не решена»,
«Моя проблема не решена», «Я так и не понял, куда обращаться» и вариант
последней без запятой. Допускаются начальные «Спасибо, но…», «Спасибо большое, но…»,
«Большое спасибо, но…» и «Понятно, но…». Поддерживаются варианты с `ё` и `е`.
Это ограниченные правила полного сообщения; произвольное понимание намерения
не заявляется. Отдельная благодарность не создаёт работу, а «Спасибо, а когда
турнир?» продолжает обычный путь нового вопроса.

Для текстового продолжения проверяются последняя закрытая карточка, отсутствие
нового предшествующего автоматического цикла и неразобранных предыдущих входов.
Явный reply может указать сохранённое сообщение закрытой карточки того же
диалога. Неясная связь оставляет текст на ручном разборе без генерации и
автоматической привязки. При подтверждённой связи создаётся дочерняя карточка,
куда попадают новый текст, вложения и уже принятые последующие сообщения.
История закрытого родителя сохраняет прежние связи и не копируется.

Миграция `0006` сохраняет старые действия активными и отклоняет обратный откат
при наличии подготовленных действий, ещё ожидающих закрытия. Для уже активированных
действий исходное закрытие сохраняется при обратном и повторном применении.
Реальные свойства callback и удобство клавиатуры проверяются отдельно по §19.4.

Воркер `run_vk_bot_sender` доставляет подготовленные части только в настроенный
пилотный диалог. Перед пилотом требуется проверить область ключа VK random_id
по §19.4. Запуск требует `VK_BOT_SEND_ENABLED=1` и `VK_SEND_ENABLED=1`.
После восстановления БД выполните `isolate_restored_bot_deliveries` в карантине
до запуска отправителей. Неопределённые части остаются закрытыми для повтора.

Миграция `support/0015_ai_uncertainty` добавляет ревизию неизвестности части и
время её фиксации. У существующих неизвестных частей ревизия устанавливается
при миграции. Журнал ответа показывает последнюю ревизию и запуск восстановления.

Для каждого нового восстановления сохраните UUID запуска и выполните команду
с этим UUID под карантином, после остановки прежних процессов приложения.

```sh
python apps/backend/manage.py isolate_restored_bot_deliveries --recovery-run-id UUID
```

Повтор завершённого UUID сохраняет результат обработки. Для следующего
восстановления используйте новый UUID. Он назначает новую ревизию неизвестности.
Журнал запуска сохраняется до обработки, а результат всего прохода фиксируется
одной транзакцией. При противоречии связей или подтверждённых исходов обработка
откатывается, запуск остаётся незавершённым для разбора и повторного выполнения.

Вызов без аргументов поддерживается для существующих инструкций. Он получает
устойчивый UUID из идентификатора инцидента карантина. Явный UUID позволяет
различать несколько восстановлений в пределах одного инцидента.

### Ручная сверка частей бота

Миграция `support/0016_ai_reconciliation` добавляет проверки и защищённые
доказательства. В журнале сохранённого ответа доступно действие «Проверить
отправку части». Для части с открытой карточкой действие доступно владельцу
или координатору, с закрытой карточкой координатору, с записью только в журнале
сотруднику с доступом к этому журналу. Повтор команды заново проверяет полномочия.

`POST /support/ai-parts/{part_id}/reconcile/` принимает JSON с `client_operation_id`.
Ответ содержит операцию `reconcile_ai_part` и запись сверки. Незавершённая проверка
возвращает `202`, завершённый повтор `200`. Параллельная новая команда получает
`409 reconciliation_in_progress`. `GET /support/ai-parts/{part_id}/state/`
возвращает состояние доставки и последнюю проверку текущей ревизии.

Исполнитель запускается отдельно с заданными `VK_GROUP_ID` и
`VK_LONG_POLL_PILOT_PEER_ID`.

```sh
python apps/backend/manage.py run_vk_bot_reconciliation --once
```

Локальное отсутствие допуска проверяется по попытке и заданию в актуальной БД.
Чтение истории использует `VK_HISTORY_CORRELATION_VERIFIED` и токен сообщества
после проверки корреляции на пилоте. Предел чтения составляет одну порцию истории
и две минуты с создания проверки. Общая квота сообщества учитывается через
существующий ограничитель истории. Ожидание квоты переносит то же задание
на следующую доступную минуту с сохранением крайнего срока и бюджета захватов.

Сверка сохраняет `accepted_by_vk`, `not_sent_verified` или `unresolved`. Подтверждение
приёма связывается с исходной карточкой обработки, включая закрытую. Неизвестные
восстановленные части требуют доказательства, покрывающего восстановленный случай.
При недостатке данных состояние остаётся неизвестным. Во время нового восстановления
активные сверки завершаются с `recovered_from_backup`, а прежние аренды отзываются.
Следующая проверка использует новую ревизию неизвестности и новый UUID команды.

### Автоматическая постановка и квота истории

Примените миграции `vk_channel/0004_history_budget` и `support/0017_auto_scan`.
Для включения автоматической постановки задайте `VK_BOT_RECONCILIATION_AUTO_ENABLED=1`
и запустите `run_vk_bot_reconciliation` с настроенным сообществом и пилотным диалогом.
Постановщик использует локальное доказательство отсутствия допуска либо проверенную
корреляцию истории при `VK_HISTORY_CORRELATION_VERIFIED=1` и заданном токене.

За проход просматриваются 25 неизвестных доставок в порядке времени и ID.
Курсор сохраняется в БД и продвигается за пропущенные записи. Завершённая либо
принятая ручная проверка этой ревизии исключает автоматическое дублирование.
После `unresolved` следующая проверка той же ревизии запускается сотрудником.
Автоматические проверки имеют отдельный устойчивый ключ и меньший приоритет
в очереди. В журнале они отмечены как автоматические.

Фиксация неизвестного исхода уведомляет исполнителя через PostgreSQL после коммита.
Исполнитель также опрашивает кандидатов каждые пять секунд. При выключении автоматики
уже поставленные автоматические проверки завершаются с `automation_disabled`,
после чего сотрудник может запустить ручную сверку.

Предварительная общая квота составляет 12 чтений в минуту на сообщество.
Автоматические сверки и фоновое восполнение истории вместе используют до 6 чтений.
Оставшиеся чтения доступны ручным сверкам. Один внешний запрос истории на сообщество
исполняется одновременно во всех процессах приложения. Блокировка PostgreSQL
