## С чего продолжить

Локальный контур §16.24–16.25 готов: подготовка по UUID, проверка доступа к исходному сообщению, выдача и диапазоны аудио, неизменный срок 168 часов, ссылки и защиты чтения CAS, очистка и восстановление. Главные файлы — `apps/backend/support/attachments.py`, `apps/backend/support/attachment_source.py` и `apps/backend/storage/cas.py`. Миграции: `storage/0001_initial`, `support/0008_attachment_cache`. Команды для очистки и восстановления описаны в README. Получение из ВК отключено по умолчанию; оригиналы без сохранённого URL и обновление истёкшей ссылки требуют проверенного способа чтения. На стенде ещё проверить хосты CDN, форматы, истёкшие ссылки, права токена, диапазоны на телефоне и предел передачи в веб-сервере.

Локальный контур §19.1 дополнен задачей чтения, отчётом о покрытии, общей квотой со сверкой и подтверждением границы. Миграция `vk_channel/0002_gap_history`. Чтение выключено по умолчанию. Команды `run_vk_gap_history`, `mark_restored_vk_gaps` и `resume_vk_gap` описаны в README. На тестовом сообществе предстоит подтвердить права, идентичность сообщений, границы страниц и покрытие. До подтверждения истории разрывы остаются на ручном разборе.

§19.3 подключён для человеческих карточек. `message_event` дедуплицируется, действие и подтверждение сохраняются отдельно от переписки, закрытие отменяет неначатые отправки, продолжение ссылается на исходную карточку. При пилотном переключателе ответ менеджера выдаёт «Вопрос решён». Остаются выдача других кнопок из соответствующих сценариев, автоматические вопросы и пилот формата/срока подтверждений. Миграции `support/0009_student_actions` и `vk_channel/0003_student_actions`.

Добавлены индивидуальные блокировки восстановления по §15.10 и цели сверки по §16.20. Команда `recover_support_delivery --recovery-run-id UUID` сначала сохраняет запуск в журнале БД, затем под общим карантином атомарно переводит незавершённые отправки в неизвестность, завершает восстановленные проверки и блокирует восстановленные `failed`. Повтор завершённого UUID ничего не меняет; новое восстановление заменяет прежнюю блокировку. Миграция `support/0010_response_recovery` сохраняет старые запреты и дополняет точные связи заданий.

Подтверждение из подставной истории снимает блокировку без новой попытки, сохраняя прежние отказы и черновик. Доказанная неотправка поддержана только для отсутствия допуска всех попыток в актуальной, не затронутой восстановлением БД. Пустая история и `started_at=NULL` после восстановления не разблокируют ответ. Источник доказательства отрицательного исхода за весь восстановленный интервал пока отсутствует; до его проверки запрет сохраняется. `run_support_sender --reconcile-only` допускает локальную проверку без токена и включения сетевого чтения. Полное восстановление предметной копии остаётся отдельной приёмкой §9.4.2.

Главная и внутренние уведомления §27.4 добавлены в модуле `apps/backend/workspace/`. Допущенный сотрудник видит свои назначения, свободную очередь и сводку поддержки в пределах доступа. Недоступные будущие модули не подменяются показателями. Ошибки блоков и счётчика отличаются от пустого состояния; отдельный блок можно загрузить повторно. Остальные состояния входа и допуска продолжают использовать accounts.

Миграция `workspace/0001_initial` добавляет ленту с уникальностью «исходное событие, получатель». Взятие, перехват и передача создают личное уведомление новому владельцу в одной транзакции с назначением. Исторические назначения остаются без вымышленных новых уведомлений. `GET /staff/notifications/` поддерживает HTML и JSON с постраничным списком и общим числом новых. `POST /staff/notifications/{id}/read/` сохраняет первое серверное время; повтор и параллельные запросы его не меняют. Переход открывает исходную карточку с независимой проверкой доступа; прочтение не закрывает обращение.

Начат 1Г: `apps/backend/knowledge/` содержит каталог материалов и текстовые черновики по первой части §18.2. Миграция `knowledge/0001_initial` создаёт `kb_document`, `kb_document_version` и журнал `kb_command`. Каждый материал может иметь независимые черновики. Создание и сохранение используют UUID сотрудника; точный повтор возвращает исходные ID и сохранённую ревизию вместе с текущим состоянием, не затирая последующие правки. Сохранение проверяет `expected_draft_revision`; при конфликте HTML показывает текущий текст и сохраняет ввод в редакторе. Допуск к поддержке и принадлежность версии материалу проверяются сервером, включая повтор команды.

Поддерживается обычный текст до 64 КиБ UTF-8. Миграция `knowledge/0002_text_preparation` добавляет запись подготовки и снимок. POST подготовки привязан к ревизии, повтор UUID возвращает исходную запись. После сохранения правок активная задача прежней ревизии отменяется. Готовый текст доступен в предпросмотре со статусом `source_prepared`. Миграция `knowledge/0003_fragment_index` добавляет индексирование снимка по §9.20. Отдельный воркер `run_worker --knowledge-index-only` вычисляет E5 и сохраняет неактивное поколение с русским полнотекстовым индексом. Режим проверен на настоящей модели из закреплённой ревизии, запуск описан в README. По §18.1–18.2 подключены публикация, замена, снятие и сверка черновика, а также гибридный поиск только по действующим снимкам. `knowledge/0004_publication` добавляет события публикации, команда `isolate_restored_knowledge` изолирует восстановленные публикации до повторной проверки. Реальный запрос E5 проверен локально. По §18.4 доступны поиск и вставка фрагмента в карточке поддержки, создание закрытого черновика из выбранного вопроса и подтверждённого ответа. Миграция происхождения — `knowledge/0005_support_origin`. Полный локальный прогон — 143 теста Django на PostgreSQL. Последний отдельный прогон Node.js — 2 теста.

По §10.2 и §10.7 подключена немедленная передача по однозначной текстовой просьбе и распознавание короткой благодарности после закрытия. Причина и событие сохраняются в карточке через миграцию `support/0011_explicit_handoff`. Миграция `support/0012_ai_processing` добавляет версии автоматического вопроса и входы попыток. Диагностический поиск запускается отдельной командой и возвращает вопросы на ручной разбор. Журнал §16.22 показывает завершённые попытки без ответа и сохранённые ответы. Миграция `support/0013_ai_answer_snapshot` добавляет снимок ответа и ожидающую доставку. Предпросмотр генерации через локальный llama-server проверен с подставным HTTP-сервером. Он сохраняет только дословную выдержку после повторной проверки источника. Миграция `support/0014_ai_part_delivery` добавляет попытки доставки и общий реестр ключей VK. Воркер допускает и отправляет части последовательно, проверяет актуальность и сохраняет поздний исход. Прогон выполнен с подставным транспортом. Настоящий Qwen и реальная отправка ждут пилота. Следующий блок 1Г — сверка неизвестных частей, подключение менеджера и остальные сценарии §10 и §15.11–15.12. Файлы и Google требуют отдельной подготовки.

## Как запускать и проверять

Команды запуска и переменные среды описаны в [README серверной части](../apps/backend/README.md) и [шаблоне среды](../.env.example). Используй отдельную PostgreSQL для разработки и тестов. Для поиска на кириллице нужна сортировка `und-x-icu`. Из корня репозитория, с настроенной средой:

```sh
bash apps/backend/scripts/build_static.sh
python apps/backend/manage.py migrate
APP_ENV=production python apps/backend/manage.py collectstatic --noinput
python apps/backend/manage.py test apps/backend
python apps/backend/manage.py makemigrations --check --dry-run
node --test apps/backend/support/tests/polling.test.mjs
```

Пилот ВК готовится отдельно в действующем сообществе «Баскетбол в МИРЭА». Локальный `.env` на Mac хранится вне Git. В нём заданы сообщество и разрешённый личный диалог. Читатель отбрасывает все остальные события до журнала, карантина и очереди. Не включай Long Poll и отправку без отдельной задачи на пилот. Сетевые переключатели в шаблоне выключены.

На текущем ПК подготовлены отдельные контейнеры `alliance-spec-test-pg` и `alliance-spec-test-python`, после проверок они остановлены. Локальная `.env.testing` исключена из Git. Для повторного прогона запустите оба контейнера, затем `docker exec alliance-spec-test-python python apps/backend/manage.py test apps/backend --noinput`. Не запускайте параллельно второй набор Django на той же тестовой БД. Сборка на Linux проверялась в временной копии файлов с LF: текущий Windows checkout использует CRLF.

Пользователь просит следовать согласованной спецификации и экономить токены. Читай нужные подразделы и ограничивай вывод логов и тестов итогами и ошибками.
