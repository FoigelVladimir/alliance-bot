## Разделение работы

Фронтенд: компоненты, адаптация, состояния загрузки/ошибок и подключение согласованного API. Браузер не источник полномочий.

Сервер: VK ID/сессии, проверка каждого действия, общая база, один владелец обращения, история, версии документов, идемпотентность, неизвестный исход отправки и повторные события ВК.

Поиск/модель: только подготовленные опубликованные источники, диагностика версий, измерение качества/задержки, честный отказ, пауза AI после передачи людям.

Запуск: выбрать реальный способ доступа, автозапуск, копии и восстановление. Локальный HTTP-сервер предназначен только для просмотра.

## Что уточнить до зависимой части спецификации

- Реальные документы клуба, примеры вопросов и разрешённые ожидаемые ответы; образцы форм и таблицы руководителя.
- Доступы и возможности приложения VK ID и сообщества; проверенная связь идентификаторов, фактическое право писать каждому адресату.
- Поддерживаемый формат первого турнира и его правила; текстовая форма доски не задаёт правила всех видов спорта.
- Точные контракты уже согласованных прав и восстановления доступа: см. docs/СПЕЦИФИКАЦИЯ.md §9.12–9.13. Отказ и блокировка — разные состояния; повторная заявка не обходит блокировку.
- Реальная нагрузка и границы приёмки модели: объём вопросов, параллельность, измерение полной задержки. Цель 4–5 секунд не заменяет испытание.

Это исходные неизвестные. Продуктовые решения обсуждаются, технические выбираются с обоснованием, внешние доступы проверяются. Каждое неизвестное относится к своему этапу; поздние турниры не блокируют первый серверный путь поддержки.

## Как принимать завершённый этап

- Есть конкретный сценарий с входными данными и наблюдаемым результатом, а не только визуальный экран.
- Проверены применимые права, ошибка и повтор действия; перечень и результат проверки записаны.
- Есть команды запуска, изменения настроек/миграций и границы реализованного.
- Демо, mock и внешние неподключённые сервисы обозначены; технический эксперимент не называется рабочей интеграцией.
- Этап закоммичен и связан с соответствующей частью спецификации. Неподтверждённые критерии остаются открытыми.

Полный MVP считается готовым после реализации и сквозной проверки всего включённого объёма, а не только первой очереди поддержки. Фактические результаты нельзя заменять утверждением «код написан по документу».

### Аварийное назначение руководителя на восстановленной базе

1. Перед открытием восстановленной базы для запросов остановите старые веб-процессы и фоновых исполнителей. Запустите веб-процессы с новым `STAFF_QUARANTINE_INCIDENT` во всех экземплярах. До сверки не запускайте отправки.
2. Получите подтверждение полномочий по независимому каналу клуба. Сохраните его вне рабочей базы и репозитория. Для служебных команд подготовьте доступный ответственному файл JSON с полями `incident` (тот же идентификатор), `profile_id` (ID выбранного внутреннего профиля), `reference` (ссылка на внешнее подтверждение) и `expires_at` (дата и время ISO 8601 с часовым поясом). Файл служит вводом оператора, происхождение подтверждения проверяет ответственный.
3. Запустите `python apps/backend/manage.py begin_staff_leader_recovery --profile-id ID --expected-identity-version VERSION --authority-file FILE`. Передайте одноразовую ссылку по проверенному каналу. Руководитель проходит подтверждение VK ID.
4. Запустите `python apps/backend/manage.py assign_emergency_staff_leader --recovery-id ID --authority-file FILE --responsible OPERATOR`. При подтверждённом переносе из пустого профиля укажите `--transfer-empty-profile-id ID`. Профиль с историей остаётся конфликтом для отдельной сверки.
5. Руководитель входит заново. Карантин других профилей сохраняется в БД. Сверку, снятие карантина и возобновление фоновых отправок проводите отдельно по §9.4.2 и §26.
