# Результаты приёмки MVP «Альянс»

## Предварительная проверка очереди перед 1А

Проведена 7 ноября 2026 года на базе коммита `98beead`. Это испытание кандидата по §9.19 и §29.2 [спецификации](СПЕЦИФИКАЦИЯ.md).

Среда — macOS arm64, Python 3.14.5, Django 5.2.19, psycopg 3.3.8, psycopg-pool 3.3.3, Procrastinate 3.10.0, PostgreSQL 16.15. Одноразовый кластер использовал только Unix-сокет в закрытом временном каталоге. Для постановки использован DjangoConnector, для запуска — штатный исполнитель Procrastinate.

| Сценарий | Результат |
| --- | --- |
| Постановка вместе с предметной записью | Пройдено. При принудительном откате Django-транзакции исчезли обе записи. При коммите сохранились обе. |
| Получение сохранённой задачи после перезапуска | Пройдено. Новый процесс исполнителя выполнил сохранённое задание. Отдельно перезапустили PostgreSQL до запуска исполнителя. Задача была выполнена один раз. |
| Атомарное завершение задачи и предметной записи | Штатный исполнитель не прошёл. После коммита предметного результата процесс был принудительно остановлен до возврата из обработчика. Предметная запись осталась, задача осталась в `doing`. |
| Завершение прежним исполнителем после повторного захвата | Штатное завершение не прошло. Через функции той же схемы задачу захватил исполнитель A, задача была возвращена в очередь и захвачена B. Вызов `procrastinate_finish_job_v1` со старым ID задачи принял завершение, несмотря на сохранённое владение B. Это проверка SQL-пути штатного завершения. Истечение аренды отдельным таймером не воспроизводилось. |
| Потеря подтверждения после допуска к отправке | Пройдено с прикладной защитой в тестовом обработчике. Тайм-аут имитировал потерю подтверждения. Ответ и попытка получили `unknown_outcome` в одной транзакции. При повторном вызове обработчик не допустил вторую внешнюю попытку. Статус задачи самой библиотеки стал `succeeded`, а предметный исход остался неизвестным. ВК в испытании не вызывался. |

**Решение для 1А.** Выбрать предусмотренную §9.19 ограниченную собственную очередь на PostgreSQL. У штатного исполнителя кандидата завершение отделено от предметной транзакции, а путь завершения не проверяет владение. Прикладная защита от повторного внешнего вызова сама по себе эти два условия не закрывает. Вывод относится к проверенной версии и штатному пути исполнения. Собственный адаптер поверх библиотеки не испытывался. [Документация Procrastinate о транзакционной постановке](https://procrastinate.readthedocs.io/en/main/howto/production/external_connection.html)

Граница интерфейса 1А. Прикладная операция ставит задачу с устойчивым ключом внутри текущей транзакции. Исполнитель при захвате получает токен владения и срок. Допуск к внешнему вызову и фиксация результата проверяют токен, срок по времени БД и допустимое состояние. Терминальный результат задачи и связанные предметные изменения фиксируются вместе. После возможной отправки без подтверждения повтор блокируется до сверки. Состав файлов выбранной ветки берётся из §29.2 и утверждается перед началом 1А. Эти свойства предстоит подтвердить тестами реализации.

Команды прогона. Во временной среде выполнено `python3 -m venv venv`, установлены `Django==5.2.19`, `psycopg[binary]==3.3.8`, `psycopg-pool==3.3.3` и `procrastinate==3.10.0`. Одноразовый PostgreSQL поднят через `initdb` и `pg_ctl`. Тестовый скрипт запущен как `venv/bin/python probe.py` на пустом кластере. Для отдельной проверки перезапуска записали задачу, выполнили `pg_ctl -D data -w restart -m fast` и запустили `venv/bin/python probe.py worker durable`. Тестовый скрипт этого прогона находился в `/tmp/alliance-queue.7HhVZX/probe.py`. Производственные файлы и зависимости в репозитории не менялись.

Девять новых тестов покрывают обработку VK ID через подставные ответы, отказ и повторную заявку, защиту CSRF, повтор и отмену возврата, конкурентный первый вход, делегирование, отзыв, повторный допуск и восстановление обычной руководящей привязки. На стенде отдельно проверяется конфигурация доступа и журналов HTTPS-прокси.

Завершение назначений секций и иных делегирований при отзыве нужно подключить при появлении соответствующих модулей. На 1Б отзыв повышает поколение допуска и закрывает рабочий доступ к текущим маршрутам.

#### Очистка временных данных входа

Команда `python apps/backend/manage.py clear_expired_staff_login` удаляет истёкшие попытки входа, в том числе прерванные обмены с провайдером, и стирает временное доказательство незавершённого восстановления после истечения его срока. Состояние завершённого восстановления и журнал остаются доступны для проверки. Для стенда запускать раз в минуту штатным планировщиком с той же конфигурацией БД, что у Django. Планировщик рабочего размещения ещё не настроен. На PostgreSQL проверены граница срока, повторный запуск очистки и отказ в восстановлении, срок которого истёк до получения последней блокировки.

#### Аварийный режим 1Б

До правок добавлены к перечню `apps/backend/accounts/management/commands/assign_emergency_staff_leader.py` и `apps/backend/accounts/migrations/0002_accesscontrol_quarantine_incident_and_more.py`. Аварийный режим использует отдельный идентификатор инцидента в настройках среды и внешнее подтверждение полномочий в файле вне рабочей базы.

Синтетический прогон на PostgreSQL проверяет вход в карантине, внешний документ, подтверждение нового VK ID через подставной ответ, однократную запись назначения, закрытые старые сеансы и отказ при конфликте с профилем с историей. После аварийного назначения идентификатор карантина сохраняется в БД. Только подтверждённый профиль может снова войти, и только после нового входа. Остальные профили остаются закрытыми.

Этот прогон покрывает аварийное назначение сотрудника. Полный регламент восстановления БД, групповой сверки прав, снятия карантина и фоновых отправок по §9.4.2 и §26 проверяется отдельно. Вызовы VK ID на зарегистрированном стенде, реальный источник подтверждений клуба и восстановление из резервной копии в этом прогоне не использовались.

### 1Г. Ревизии неизвестности частей бота — результат

Изменения продолжают реализацию товарища из `7471b25`. Обычный неизвестный исход, истечение аренды и восстановление сохраняют ревизию неизвестности и время.
